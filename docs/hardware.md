Atlas is built mainly from reused and second-hand desktop components. The hardware was not selected as one finished server specification; it has developed incrementally as the project's storage, media, and development roles have grown.

## Origins and reuse

The original machine was an old family computer that my parents no longer needed. Additional parts came from another unwanted computer belonging to my housemate, allowing the first useful version of Atlas to be assembled without buying a purpose-built server.

The motherboard was purchased second-hand after being advertised as having a faulty PCIe x16 slot. Inspection showed that the slot was missing its retention clip rather than being electrically unusable. The graphics card could still be secured through the case's expansion-slot mounting point, and the resulting system has operated reliably.

This approach made troubleshooting and hardware evaluation part of the project. It also means that reliability cannot be assumed from the age or origin of a component: disk health, service recovery, and off-site backups are treated as separate responsibilities.

## Storage roles

The SSD holds the operating system and latency-sensitive state, including application configuration, databases, Git metadata, and active development files. The hard drives provide bulk capacity through a mergerfs pool.

mergerfs presents the disks as one logical pool while retaining ordinary filesystems underneath. That supports incremental expansion and mixed-capacity drives, but it does not provide RAID redundancy, parity, or native snapshots. A failed disk can still mean the loss of files stored on that disk, so important data needs independent backup coverage.

The detailed placement, backup coverage, and recovery limitations are documented in [Storage and backups](storage-and-backups.md).

## GPU workloads

The GTX 970 supports workloads that benefit from hardware acceleration without requiring a newer dedicated server platform. Current uses include Jellyfin media processing and Immich machine-learning features.

The card's age and software compatibility are practical constraints. GPU-dependent application changes need to be tested against the actual hardware rather than assuming that every current image or acceleration path will remain compatible.

## Constraints and trade-offs

- **Cost versus efficiency:** reused hardware reduced the cost of building Atlas, but it is less power-efficient than a newer purpose-built system.
- **Flexibility versus redundancy:** mergerfs makes storage growth straightforward, but protection comes from monitoring and backups rather than disk-level redundancy.
- **Consumer platform versus server features:** the current system provides enough capacity for the workload, but it does not offer features such as hot-swap bays, ECC memory, or remote management.
- **Incremental upgrades versus replacement:** changing one constraint at a time keeps the project affordable and understandable, but requires careful compatibility and recovery planning.

## Potential improvements

- Move to a case with more drive bays when storage expansion requires it.
- Add capacity without silently changing which data is covered by off-site backups.
- Reassess disk redundancy or parity once the storage layout and media requirements are more settled.
- Measure power use before deciding whether a platform replacement would provide enough practical benefit.

These are possible improvements, not scheduled purchases or completed changes. See the [Roadmap](roadmap.md) for the wider project context.

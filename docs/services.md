## Operations and monitoring

| Service or mechanism | Responsibility |
| :-- | :-- |
| Uptime Kuma | Checks availability through the normal private access path and reports failures |
| smartd | Monitors disk health |
| Post-boot verification | Confirms that important services, storage, access, and hardware recover after a restart |
| Cockpit | Host administration and system inspection |
| Homer | Private navigation page for the service collection |
| Dozzle | Read-only access to container logs |
| NetAlertX | Local-network device discovery and change awareness |

Monitoring is layered. Container health checks provide local application signals, Uptime Kuma checks the path a user normally takes, and host-level checks cover disks, mounts, native services, and recovery after boot.

## Backup services

Backrest is the management and monitoring interface for the backup system, with restic as the backup engine and Backblaze B2 as the encrypted off-site destination.

Applications are not all backed up in the same way:

- Ordinary configuration and application files can be copied directly when they are safe to restore as files.
- Relational databases use prepared dumps rather than copies of live database directories.
- Nextcloud uses a consistent staging copy containing the files and matching database material.
- Selected bulk libraries are included according to their value and recovery requirements.
- Reproducible caches, container images, empty libraries, and replaceable media can remain outside the backup set.

Exact coverage and tested recovery boundaries are recorded in [Storage and backups](storage-and-backups.md).

## Deployment boundaries

- Docker Compose separates most applications and their dependencies into independently maintained projects.
- Native systemd services handle responsibilities that belong to the host rather than one application stack.
- Application state and databases live on SSD storage where latency matters.
- Large libraries use the mergerfs pool.
- Web interfaces and SSH are private rather than public internet endpoints.
- Production configuration, ports, addresses, credentials, and schedules are not included in this public repository.

## Service lifecycle

Service changes are treated as maintenance work rather than casual container replacement. A meaningful change should account for:

1. Persistent data and rollback requirements.
2. Dependencies on databases, storage, networking, or GPU support.
3. Monitoring and restart behaviour.
4. Backup coverage and restoration requirements.
5. Direct verification through the normal access path.
